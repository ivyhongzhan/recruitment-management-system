01 / THE DESIGN PROBLEM

Recruitment is a coordination problem, not just a list of names.

Recruiters need to know where an application stands, what actions are possible, and whether a change actually persisted. A useful interface should reduce ambiguity without concealing the rules behind the workflow.

Know the state

Surface the current stage and eligible next actions.

Prevent errors

Block invalid transitions and conflicting edits at the API.

Explain changes

Let a reviewer inspect the event history of an application.

02 / EXPLORE THE ARTIFACT

03 / DESIGN DECISIONS

What is built—and why?

↗

Board + table

Stage grouping supports visual scanning; the table supports focused search, filtering and detailed row operations.

↳

Guided next steps

Only valid next states are offered, and the API independently rejects invalid changes.

⎘

Application history

Record-level events make changes inspectable rather than relying on a mutable status label alone.

≡

Careful metrics

Stage counts are snapshots with an explicit denominator, not conversion rates, hiring quality or fairness evidence.

04 / SYSTEMS ENGINEERING

The interface is backed by state and persistence.

INTERACTION LAYERHTML · CSS · JavaScriptBoard, table, details, forms
↓
APPLICATION LAYERJava · Spring BootValidation, transitions, concurrency checks
↓
PERSISTENCE LAYERMySQL · Spring Data JPAJobs · Candidates · Applications · Audit events

The 2026 implementation maintains relational records, rejects duplicate applications for the same job, validates state transitions, and uses a version check to detect stale edits. MySQL stores changes across browser refreshes and application restarts.

05 / RESEARCH CONNECTION

Three doctoral perspectives, with clear evidence boundaries.

HCI

Interaction clarity and error recovery

Implemented: visible stages, alternative views, labeled controls and status feedback. To evaluate: task completion, errors, perceived clarity and accessibility with participants.

CSS

Measurement and interpretation

Implemented: present-state counts from a synthetic dataset. Not inferable: conversion, discrimination, population behavior or causal outcomes.

IS

Workflow and data integrity

Implemented: normalized entities, enforced state rules, versioned updates and record histories. Not implemented: production authentication, multi-user governance or secure live recruitment.

07 / REPRODUCE LOCALLY

Run and inspect the code.

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
docker compose up --build

Open http://localhost:8000 for the system. The backend uses Java + Spring Boot, Spring Data JPA, Flyway, and MySQL; run mvn verify for the MySQL integration tests.

All starting candidate names, email addresses, positions and stage assignments are fictional. This is a research demonstration, not production recruitment software. The 2021 undergraduate thesis used Spring Boot + MySQL; the new 2026 implementation also uses Java + Spring Boot + MySQL and is a reconstruction, not recovered thesis source.
